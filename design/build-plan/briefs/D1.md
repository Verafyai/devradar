## Today's scope (all behind `foundations`, Plan page behind `plan`)

1. **App page shell.** One shared renderer in `scripts/render-pages.mjs` (or a small module it imports) for the section 2 pattern:
   header with company switcher, breadcrumb "Apps › Name", icon tile, H1, status chip (LIVE green, BETA blue `#7FB2FF`, SOON amber),
   promise line ending "Starting from {Company}'s profile." (or the example company when signed out), input card with 2 to 4 fields
   prefilled from the saved company profile, the honest time and credit line above the run button, summary strip slot, result column,
   right rail slot, evidence expanders. Tokens exactly as spec section 2; Inter; minimum 14px; body 16px. Works at 375, 768, 1440.
   With the flag off, the nine pages render exactly as today.
2. **Sample result first.** The shell can show a sample result for the example company before a run, clearly labeled
   "Sample result for an example company" with "Run it for {Company}". Use the invented "Plinth" data from the mockups only, and keep it
   in `data/samples/<app>.json` with `"sample": true`. Never mixed with real results.
3. **Run engine.** `lib/runs.js` plus `api/runs.js`: create a run for (company, app, inputs), step list with status
   (queued, running, done, failed), heartbeat timestamp, visible failure with "Nothing was charged", result saved per company and app,
   versioned so the next run can show "changed since last run". Client shows step rows live (poll is fine). A step that has not
   heartbeated in 60 seconds shows as stalled with a retry, never a silent spinner. Stub app `echo` with 3 steps that can be told to
   fail at step 2 (for tests).
4. **Credits ledger (sample mode only).** `lib/credits.js`: a per user balance and ledger entries (reserve on start, commit on success,
   release on failure). No payment, no Stripe, no price changes, no real charges; the credit numbers per app come from a config file
   marked `"proposed": true` (Rex decides final mapping, spec section 9). Tests prove a failed run releases its reservation.
5. **Plan.** Generalize Plan items beyond events: `{type: event|content|outreach|fix|task, title, owner, date, source_app, evidence_url}`.
   `/plan` page (flag `plan`) lists items per company with owner and date, CSV and .ics export. Existing event items keep working.
   Notion and Linear export are later (D4); leave a disabled button with "Coming soon".
6. **Eval harness hooks.** `evals/` folder in the repo:
   - `evals/golden/companies.json` (the proposal above, `status: proposed`) and one folder per company with empty expectation files
     per app (`events.json`, `docs-issues.json`, `competitors.json`, `topics.json`), each `{ "items": [], "unverified": true }` unless verified with a source.
   - `evals/run.mjs <app>`: runs an app (stub `echo` today) for each golden company in sample mode, applies mechanical checks
     (pass or fail) and writes `scores/<YYYY-MM-DD>/devradar.csv` with the nine rubric categories (blank when not measured) and the
     section 4 formula. Judged checks are a JSON list with 0 to 4 anchors, filled by a reviewer, not by the code.
   - `scripts/visual-check.mjs <url> --widths=375,768,1440`: Playwright screenshots plus a horizontal overflow and 14px check.
7. **Tests** for runs (success, failure releases credits, stalled detection), credits, plan types and exports, flags off rendering.
